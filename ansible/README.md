A complete infrastructure-as-code project for learning and practicing Ansible automation using Azure cloud resources. This project separates infrastructure provisioning (Terraform) from configuration management (Ansible) following best practices.

## 📋 Project Overview

This project demonstrates a real-world DevOps workflow where:
- **Terraform** provisions cloud infrastructure (Azure VMs)
- **Ansible** manages configuration and automation tasks on those VMs
- Infrastructure state is maintained separately from application/configuration state

The setup creates 2 Ubuntu VMs in Azure that serve as managed nodes, while your local WSL environment acts as the Ansible control node.

### Why Separate `app/` and `terraform/`?

**Separation of Concerns:**
- **`terraform/`**: Infrastructure provisioning - Creates and manages cloud resources (VMs, networks, security groups)
- **`app/`**: Configuration management - Manages software, configurations, and automation tasks on those resources

**Benefits:**
- Infrastructure changes don't require modifying automation scripts
- Ansible playbooks can be tested locally before deploying to cloud
- Different team members can work on infrastructure vs. configuration independently
- State management is cleaner (Terraform state vs. Ansible facts)

## 🚀 Getting Started

### Prerequisites

1. **Azure CLI** - Authenticate with Azure
   ```bash
   az login
   ```

2. **Terraform** - Version >= 1.0
   ```bash
   terraform --version
   ```

3. **Ansible** - Installed on WSL/Linux
   ```bash
   ansible --version
   ```

4. **SSH Key Pair** - For VM access
   ```bash
   ssh-keygen -t rsa -b 4096 -f ~/.ssh/azure_ansible_key
   ```

### Initial Setup

1. **Configure Terraform Variables**
   ```bash
   cd terraform
   cp terraform.tfvars.example terraform.tfvars
   ```

2. **Edit terraform.tfvars**
   ```hcl
   admin_username = "azureuser"
   ssh_public_key = "ssh-rsa AAAAB3Nz... your-public-key"
   location       = "East US"
   ```

3. **Initialize Terraform**
   ```bash
   terraform init
   ```

4. **Deploy Infrastructure**
   ```bash
   terraform plan
   terraform apply
   ```
   
   ✅ This will automatically generate `app/inventory.ini` with your VM IPs

## 📝 Useful Commands

### Terraform Commands

```bash
# Navigate to terraform directory
cd terraform

# Preview infrastructure changes
terraform plan

# Apply infrastructure changes
terraform apply

# Show current infrastructure state
terraform show

# List all resources
terraform state list

# Destroy all infrastructure
terraform destroy

# Destroy while preserving inventory.ini (see Tips section)
terraform state rm local_file.ansible_inventory
terraform destroy
```

### Ansible Commands

```bash
# Navigate to app directory
cd app

# Test connectivity to all hosts
ansible all -m ping

# Run a specific playbook
ansible-playbook playbooks/remote/check-remote-clients.yml

# Run playbook with verbose output
ansible-playbook playbooks/remote/setup-apache.yml -v

# Run playbook on specific host
ansible-playbook playbooks/remote/add-user.yml --limit client-1

# Check playbook syntax
ansible-playbook playbooks/remote/setup-apache.yml --syntax-check

# Dry run (check mode)
ansible-playbook playbooks/remote/setup-apache.yml --check

# List all hosts in inventory
ansible-inventory --list

# SSH into a managed node
ssh -i ~/.ssh/azure_ansible_key azureuser@<PUBLIC_IP>
```

### Azure CLI Commands

```bash
# Login to Azure
az login

# List all VMs
az vm list -o table

# Show VM details
az vm show -g rg-ansible-lab -n client-1

# List public IPs
az network public-ip list -g rg-ansible-lab -o table

# Start/Stop VMs (cost saving)
az vm start -g rg-ansible-lab -n client-1
az vm stop -g rg-ansible-lab -n client-1
```

## 💡 Important Tips

### 1. Inventory File Recreation

**⚠️ Important:** The `app/inventory.ini` file is automatically generated by Terraform and will be **recreated** every time you run `terraform apply` and **deleted** when you run `terraform destroy`.

**Why this happens:**
- The inventory file is managed by the `local_file.ansible_inventory` resource in Terraform
- Terraform tracks this file in its state and recreates it to match the template
- When destroying infrastructure, Terraform also removes all tracked files

**Best practices:**
- ✅ **DO NOT** manually edit `app/inventory.ini` - changes will be overwritten
- ✅ Edit `terraform/inventory.tpl` template instead if you need to modify the format
- ✅ To preserve the file during `terraform destroy`, remove it from Terraform state first:
  ```bash
  terraform state rm local_file.ansible_inventory
  terraform destroy
  ```

### 2. SSH Key Management

- Keep your private key (`~/.ssh/azure_ansible_key`) secure and never commit it to Git
- The public key is stored in Terraform state - rotate keys periodically
- Use `ssh-add ~/.ssh/azure_ansible_key` to add key to SSH agent

### 3. Cost Optimization

Azure VMs cost money even when idle. To minimize costs:

```bash
# Stop VMs when not in use (you still pay for storage)
az vm deallocate -g rg-ansible-lab -n client-1
az vm deallocate -g rg-ansible-lab -n client-2

# Start VMs when needed
az vm start -g rg-ansible-lab -n client-1
az vm start -g rg-ansible-lab -n client-2

# Or destroy everything when done learning
cd terraform
terraform destroy
```

### 4. Handling Terraform State

- Never delete `terraform.tfstate` manually - it tracks your infrastructure
- Use `terraform state` commands to manage state safely
- Consider using remote state (Azure Storage) for team collaboration

### 5. Ansible Configuration

The `app/ansible.cfg` file contains important settings:
- `host_key_checking = False` - Useful for lab, but disable in production
- `private_key_file` - Ensure this path matches your SSH key location
- `become = True` - Enables privilege escalation (sudo)

### 6. Testing Before Deployment

Always test Ansible playbooks safely:

```bash
# Check syntax
ansible-playbook playbooks/remote/setup-apache.yml --syntax-check

# Dry run (no changes made)
ansible-playbook playbooks/remote/setup-apache.yml --check

# Run on one host first
ansible-playbook playbooks/remote/setup-apache.yml --limit client-1

# Then run on all hosts
ansible-playbook playbooks/remote/setup-apache.yml
```

### 7. Debugging Issues

```bash
# Increase verbosity (-v, -vv, -vvv, -vvvv)
ansible-playbook playbooks/remote/setup-apache.yml -vvv

# Test SSH connection directly
ssh -i ~/.ssh/azure_ansible_key azureuser@<PUBLIC_IP>

# Check Ansible can reach hosts
ansible all -m ping -vvv

# Verify inventory
ansible-inventory --list
```

## 🔒 Security Considerations

- **Never commit** sensitive files to Git:
  - `terraform.tfvars` (contains configuration)
  - `*.tfstate` files (contain sensitive data)
  - SSH private keys
  - `app/inventory.ini` (contains public IPs)

- Use `.gitignore` to exclude these files
- Consider using Azure Key Vault for production secrets
- Rotate SSH keys and passwords regularly
- Lock down NSG rules to specific IP addresses in production
